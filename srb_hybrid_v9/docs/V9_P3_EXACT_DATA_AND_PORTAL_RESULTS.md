# V9 P3：精确数据、路径复用与 Portal/Landmark 结果

## 最终结论

本轮不是把公开百万条答案背进二进制，而是完成了三项可泛化改进：

1. 离线按相同源端点共享一次 Dijkstra，批量生成精确 Golden；
2. 从精确数据中学习仅用于 `Chebyshev <= 8` 的三张小型残差表；
3. 把 Grid 与 Block 边界 Portal 预计算成 26 个 ALT Landmark，为在线有界 A* 提供方向安全的下界。

公开 1M 的结果如下：

| 版本 | Accuracy | 相对 V8 |
|---|---:|---:|
| V8 快速模型 | 94.603473961 | — |
| V8 + 精确数据记忆表 | 94.612789105 | +0.009315144 |
| V8 + 精确数据记忆表 + 有界精确分支 | **94.613722680** | **+0.010248719** |

Windows 等价二进制连续三次输出 SHA-256 均为
`81978952A1FC58A537E76FC731434128AB8503CB9855500B7C875670F5AACC54`；三次百万条耗时为
1.06924、1.07176、1.18488 秒。最终 Linux 静态提交文件为 20,733,408 字节，小于 100,000,000 字节，
SHA-256 为 `8790A5C53B643B55C8B68423E8470EB857DC6FD422D3ED9A5AFF4D14C281C4CB`。

## 1. 精确 Golden 如何扩充

新增的 `offline_grouped_labeler.cpp` 不再对每条查询重新运行一次 A*。输入先按完整 `From` 排序，
同一源端点的所有目标共用一次正向 Dijkstra：一个状态只展开一次，却可以同时回答几千个目标。
若人为设置的组预算耗尽，只有尚未被证明的目标才回退到逐条无界 A*，不会把未完成的候选路径误当答案。

本轮数据规模：

| 项目 | 数值 |
|---|---:|
| 生成请求 | 1,000,000 |
| 不同完整源端点 | 200 |
| 可达精确标签 | 962,554 |
| 不可达 | 37,446 |
| 共享搜索总展开 | 633,722,836 |
| 共享搜索时间 | 693.674 秒 |
| 逐条回退 | 0 |

采样保留了公开请求的端口对分布，并强化短距离与 Block 边界：0–16、17–32、33–64 分别占
54.3%、31.5%、14.1%。分层抽取的 20 条官方 Golden 审计中，无界搜索为 20/20 完全一致。

## 2. 连续跑道为什么没有直接继续收缩

原求解器已经把 `Input -> Arc -> Output -> Net -> 下一 Input` 收缩成一条宏边。对 160 个持久路由状态审计后，
没有发现“入度和出度都为 1、可无条件继续合并”的跑道状态；所有状态都可能在水平/垂直方向分支。
因此，继续按普通链收缩会丢掉可选路径，不能保证 Golden 等价。

本轮采用的下一层压缩不是错误地合并分支，而是：

- Gap 继续用解析式前缀代价，不把每条 Gap 线展开成节点；
- 重复 Block 家族保留周期结构；
- Block 边界候选 Portal 通过最远点采样压缩成 14 个 Portal Landmark；
- 再加 12 个全局 Grid Landmark，共 26 个；
- 保存 Landmark 到每个有效 cell 的有向往返下界，在线每次只激活最强的 4 个。

所有下界来自忽略端口限制的松弛图，只会低估真实代价，因此仍满足 A* 可采纳性，不会改变精确答案。
距离最大值为 7,255，可安全压成 `uint16`；编译后二组有向表约占 6.86 MB。

## 3. 86 MB 记忆空间最后存了什么

先做了严格的 80/20 留出实验。直接存 `(源端口, 目标端口, dx, dy)` 精确键，在未见测试行上的覆盖几乎为 0；
粗糙的端口族/距离分桶覆盖提高后反而降分。因此，没有用几十 MB 背公开查询。

从独立 Dijkstra 数据中蒸馏出的最佳结构只有三张加性表：

- `路由状态类别对 × 17×17 精确位移`；
- `源端口族 × 目标端口族`；
- `源路由状态 × 目标路由状态`。

它们共 156,098 个参数，量化成 Q15 `int16` 后约 305 KB；只在距离不超过 8 时访问。训练与验证按完整源端点切分，
验证端点从未参与拟合。合成留出短路径准确度增益为 +4.7783 个点，公开 1M 总准确度增益为 +0.009315。
64 棵树虽然也能提分，但在线代价更高，已被这三张表替代。

## 4. 在线精确分支

提交版仍采用确定性最大展开数 16：

1. 快速模型先给出答案；
2. 只有固定结构选择器命中的极少请求进入精确 A*；
3. A* 在堆最小下界不小于当前候选值时才宣布完成；
4. 达到 16 次展开或哈希表容量不足，立即使用快速答案；
5. 不输出“搜索到一半的最好路径”。

加入 Landmark 后，公开 `Chebyshev <= 16` 的 cap=16 完成数提升到 225，且 225/225 与 Golden 完全相等；
状态展开从最终默认请求上的 52 降为 34。对所有短请求盲目搜索仍不划算，所以默认选择器保持只选 10 条，
这 10 条全部精确完成。

## 6. 下一轮优先级

最值得继续的是把 26 个 Landmark 从“下界”升级为小型 Portal overlay：离线精确求出周期 Block 家族、Gap 区间与端口状态之间的
稀疏转移，只保存实际可达的 `(入口状态, 出口状态, 代价)`，在线再组合源/目标局部段。必须用独立端点留出和
`accuracy gain / added microseconds` 判断是否进入提交版，不能只看精确完成数。

关键文件：

- `src/offline_grouped_labeler.cpp`：共享源的一对多精确标注；
- `src/offline_exact_labeler.cpp`：带路径与摘要的无界审计；
- `tools/generate_extra_queries.py`：端口分布、距离与 Portal 分层采样；
- `tools/distill_exact_residual_tables.py`：按完整源端点留出的表蒸馏；
- `src/exact_memory_data.hpp`：最终 3 张量化记忆表；
- `tools/export_compact_graph.py`、`src/compact_landmark_data.hpp`：Portal/Landmark 下界；
- `submission/bin/estimate`：最终 Linux 提交文件。
