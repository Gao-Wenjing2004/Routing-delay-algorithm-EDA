# V9 P19～P38：残差小表审计与十亿行热路径优化

## 结论

本轮得到两个明确结论：

1. P19 的 Golden 残差 O(1) 定点小表没有通过三套数据同时增益为正的门槛，因此没有嵌入正式提交版，也没有用公开集过拟合换分。
2. P38 在不改变任何预测值的前提下，把 P25 的批量执行路径改为 SoA、AVX2 换行扫描和正式配置专用的无分支预测路径。固定核心的 2M 行 Windows 对照中，P38 相对同编译器 P25 快 `8.6562%`；另一次交替执行七轮的中位数提速为 `6.8182%`。

当前建议提交候选是 `submission_v9_p38_fast_soa_avx2.zip`。ZIP 为 `90,860,856` 字节，小于十进制 100 MB；其中 Linux ELF 为 `96,627,152` 字节。它仍需要在官方 Linux 环境实测，不能把本机投影当作正式成绩。

## 1. P19：O(1) Golden 残差小表

P19 使用无界精确搜索标签，将 P25 相对 Golden 的残差蒸馏为固定次数的 int16 数组查询，并以如下严格规则筛选：

`公开集增益 > 0 && 独立源增益 > 0 && 独立区域增益 > 0`

基线 Accuracy：

| 数据集 | P25 Accuracy |
|---|---:|
| 训练集 | 89.881952 |
| 独立源 | 91.357630 |
| 独立区域 | 90.679402 |
| 公开 1M | 94.664723 |

共评估 `1,152` 个候选，严格合格候选数为 `0`。诊断意义上最好的候选为 `ports_displacement_pair_s10`：11 次 O(1) 查询、503,629 个参数、约 0.96 MiB int16 表，但仍然同时退化：

| 数据集 | 候选 Accuracy | 相对基线 |
|---|---:|---:|
| 独立源 | 91.077384 | -0.280246 |
| 独立区域 | 90.362162 | -0.317240 |
| 公开 1M | 94.524065 | -0.140658 |

因此 P19 的失败不是表太大或定点精度不够，而是当前残差分桶不能跨源端点、跨空间区域泛化。P19 被正确拒绝，P38 继续保留 P25 的预测算法与 Accuracy。

证据：`analysis/p19_o1_fixed/pipeline_status.json` 的最终阶段为 `rejected_by_three_way_gate`，完整消融见 `analysis/p19_o1_fixed/p13_o1_ablation.json`。

本轮回归、计时、并发和正式包摘要另存于 `analysis/p38_speed_optimization/summary.json`。

## 2. P35：批量 SoA 与端点整数化

原路径为每行构造较大的 `ParsedRow`，预测和格式化阶段会重复触碰不需要的字段。P35 改为四组紧凑数组：

- 原始行切片；
- 整数化源端点；
- 整数化目标端点；
- uint32 预测值。

预测阶段只顺序读取端点数组，格式化阶段只读取原始行切片和预测值。固定核心首轮对照中，2M 行总时间由 `0.552886 s` 降至 `0.522460 s`，约快 `5.50%`。单轮总耗时有系统抖动，因此 P35 没有单独成为正式版，而是继续合入 P38。

## 3. P36：AVX2 运行时分派

P36 为换行扫描加入 AVX2 实现，并在运行时检测 CPUID/XGETBV；不支持 AVX2 或操作系统未保存 YMM 状态时自动回退标量 `memchr`。因此 ELF 仍以 `x86-64` 为基线，不会无条件执行 AVX2。

固定核心的 P35/P36 对照中：

- 解析阶段约快 `4.04%`；
- 端到端约快 `0.85%`；
- 在另一轮直接 P25/P36 对照中，总耗时差只有 `-0.089%`，属于噪声范围。

结论是 AVX2 换行扫描成本低且安全，但它不是主要瓶颈，不能单独解释需要的倍数级提速。

## 4. P38：正式配置专用无分支预测路径

P38 新增 `predict_endpoints_submission_fast`，只针对正式提交时已经固定的选项组合：

- 关闭 legacy inner Atlas；
- 开启 fused fallback；
- 开启 family residual；
- 关闭提交版不使用的诊断计数更新。

所有计算公式和查表顺序保持不变，只移除了每条查询都会执行、但结果恒定的配置分支与无用计数写入。

固定到同一 CPU 核、相同 Zig/Clang Windows 编译器、相同 2M 输入的直接 P25/P38 对照：

| 指标 | P25 | P38 | 变化 |
|---|---:|---:|---:|
| 端到端 | 0.546384 s | 0.499088 s | -8.6562% |
| 解析 | 0.158141 s | 0.130648 s | -17.39% |
| 预测 | 0.331230 s | 0.314028 s | -5.19% |
| 格式化 | 0.031593 s | 0.027036 s | -14.43% |
| 分阶段总和 | 0.520964 s | 0.471712 s | -9.45% |

该数据是短样本本机微基准；正式 Linux 上应使用后文的 `perf` 流程重测。

为降低单轮抖动的影响，又在预热后交替执行 P25/P38 各七轮。端到端中位数分别为 `0.573728 s` 和 `0.534610 s`，即 P38 快 `6.8182%`。第 6、7 轮出现明显系统噪声，但中位数仍保持正收益。后续分数投影采用这个较保守的七轮中位数，而不是只采用最快的一组。

### 三套数据逐字节回归

P25 与 P38 使用同一编译器，对三套请求分别生成完整输出；长度和 SHA-256 均完全相同：

| 数据集 | 输出字节 | 两版共同 SHA-256 | 结果 |
|---|---:|---|---|
| 公开 1M | 40,333,509 | `dc3dd91e14241c0976f692f5107f79fcc0c86f2f6d5806be2ee8a25f94e952c5` | byte-exact |
| 独立源 | 16,044,152 | `f53b99efb7025998a3df74ba3b102226eb3144c61d5e39e2c3fbf853d4b4cb27` | byte-exact |
| 独立区域 | 16,629,142 | `524707884c64fd839620da5296f82998774a6c1d09d9ebc34b0e81b54bacd1dc` | byte-exact |

所以 P38 的公开 Accuracy 仍为 `94.664723%`；独立源和独立区域也不存在任何数值回归。

## 5. 1/2/4/8 进程 CPU 时间试验

官方结果字段是 `cpu_time_ms`，因此必须同时观察墙钟和所有工作进程的 CPU 时间。每个进程处理 2M 行的本机结果：

| 并发进程 | 墙钟 | CPU 总和 | 每个 2M 任务 CPU |
|---:|---:|---:|---:|
| 1 | 0.7559 s | 0.6719 s | 0.6719 s |
| 2 | 0.6780 s | 1.2344 s | 0.6172 s |
| 4 | 0.8552 s | 3.1250 s | 0.7813 s |
| 8 | 1.0392 s | 7.3281 s | 0.9160 s |

多进程能提高吞吐墙钟，但不能降低总 CPU 时间；4/8 进程还因带宽和缓存竞争明显恶化。因此正式版继续单线程，不用并行墙钟冒充时间分收益。

## 6. Linux perf 分阶段报告

已加入 `tools/profile_linux_perf.sh`。它会：

1. 预热页缓存与运行时状态；
2. 用 `/dev/null` 隔离算法、解析和格式化的 CPU 成本；
3. 采集 cycles、instructions、branches、branch-misses、cache references/misses、page faults、context switches 和 CPU migrations；
4. 再做一次真实文件输出并保存 SHA-256，防止仅优化 `/dev/null` 的假收益。

本机没有可用的 WSL/Linux `perf`，因此本轮没有伪造 Cache Miss 结论。应在与官方尽量接近的 Linux 机器执行：

```sh
sh tools/profile_linux_perf.sh submission_p38/bin/estimate REQUESTS.csv analysis/p38_linux_perf 7
```

## 7. PGO/LTO

Windows 上用 Zig 交叉链接 ThinLTO 时遇到目标 libc/libm 符号不完整，不能作为有效测试结果。已提供基于 P38 的原生 Linux GCC 脚本 `tools/build_p39_pgo_linux.sh`：先训练 profile，再以相同对象 basename 执行 `-fprofile-use` 与 LTO，最后检查 100 MB 限制。

```sh
sh tools/build_p39_pgo_linux.sh REPRESENTATIVE_TRAIN.csv
```

P39 必须满足以下门槛才可替代 P38：

- 与 P38 在公开、独立源、独立区域三套输入上逐字节相同；
- Linux `perf` 的 task-clock 和 cycles 稳定下降；
- 真实输出计时也下降；
- ELF 仍小于 100,000,000 字节。

## 8. 当前提交物与分数投影

正式候选：`submission_v9_p38_fast_soa_avx2.zip`

| 项目 | 数值 |
|---|---:|
| ZIP 大小 | 90,860,856 B |
| Linux ELF 大小 | 96,627,152 B |
| ZIP SHA-256 | `93f39e64cf17af87722be56b9b740dca877c946a6b40781064b61c6987efb794` |
| ELF SHA-256 | `a9664b76e31443da459d46710871a9d22bb59fa3e8055064d315d8c47e8563d8` |
| 公开 Accuracy | 94.664723% |

若把本机七轮中位数的 `6.8182%` 加速乘到 P25 的 `267.6 s` 官方 CPU 外推，则：

- P38 CPU 时间约 `249.35 s`；
- TimeScore 约 `86.1470`；
- 假设 Consistency 为 100，公开集代理总分约 `93.6538`；
- 要把 CPU 压到 Accuracy=99 时总分 98 所需的 `144 s`，仍需约 `1.73` 倍加速。

若采用固定核心单轮的 `8.6562%`，对应投影是 CPU `244.44 s`、公开代理总分 `93.6948`。因此当前合理报告范围是 CPU `244～249 s`、公开代理总分 `93.65～93.69`，而不是一个虚假的精确值。

上述只是跨机器投影，不是官方成绩。更重要的是，P38 没有提高 Accuracy，距离 Accuracy 99% 仍有约 `4.34` 个百分点。不能声称当前已达到总分 98；下一轮应先在 Linux `perf` 下确认 P38/P39 的真实热点，再决定是压缩 Atlas、改输出协议热路径，还是继续开发能通过三套数据门槛的结构化小表。
