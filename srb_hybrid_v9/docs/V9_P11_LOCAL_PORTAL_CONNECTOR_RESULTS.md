# V9 P11：局部 Portal 连接器与周期核心下界

## 结论

P11 补齐了 P10 后真正缺失的接口，并完成了不读取真实 Entry/Exit 标签的局部连接器消融：

1. P6/P9 定价器原先只能把普通 Output 当作终点，不能直接终止在 Routing Input。因而第一轮中目标端大多可达，源端 `190/190` 全部不可达。这是接口缺失，不是 Portal 模型错误。
2. 增加“Routing Input 对应路由状态可作为零代价终点”后，普通 Output 查询的 `442/442` 回归语义完全不变。
3. 只按局部连接代价选 Portal 时，Beam32 Accuracy 为 `91.567939%`。加入周期矩阵的行/列最小代价下界后，Beam32 提升到 `94.221235%`，且所有配置均无低估。
4. 把局部模板候选由 5 增至 16 后，全事件组合的研究上限达到 `99.087925%`；Beam512 已达到 `99.008109%`。
5. 不需要独立保留 512×512 组合。保留 32 个入口、对出口做条件联查时达到 `98.258958%`；64 个入口达到 `98.658770%`。下一步应压缩“给定入口后的出口候选”，而不是扩大 Portal 矩阵。

当前结果仍然是 190 条跨完整周期 Block 的定向 Teacher 子集，不是公开 1M 或官方 1 亿总成绩。当前每请求枚举两端各 1,920 个事件，仅用于研究上限，不能提交。因此正式版本仍保持 P8，不切换到 P11。

## 1. 修复的接口问题

Portal 事件定义为某条 Net 跨过周期边界后落到的第一个 Routing Input。旧结构定价器的目标连接只包含：

```text
路由状态 -> Arc -> 普通 Output
```

但源端局部连接所需的是：

```text
原始 From -> 若干路由段 -> Portal Routing Input 状态
```

因此对 Portal 输入端口，目标连接器必须是“对应路由状态、附加代价 0”。P11 在 `Pricer::query` 中只对 Routing Input 启用该终止方式；普通 Output 仍使用原 `target_arcs_`。

回归使用 442 条 P9 Block Portal 候选：

| 项目 | 旧定价器 | P11 定价器 |
|---|---:|---:|
| 行数 | 442 | 442 |
| 可达 | 390 | 390 |
| 完全相同 | 102 | 102 |
| Accuracy | 88.3989% | 88.3989% |
| 语义字段不一致 | - | **0** |

比较字段包含 `From/To/Golden/Predicted/Candidates/ValidCandidates/Transitions`；计时不参与一致性判断。

## 2. 严格的无标签评估方法

对 P10 可严格三段分解的 190 条 Teacher 请求：

1. 仅从查询坐标推导首、尾周期边界；190 条均与真实分解边界一致。
2. 在 `x=70..75, 90..95` 上枚举方向兼容的 1,920 个事件。
3. P6 结构模板生成器和 P9 轴向定价器分别估算源到入口、出口到目标的局部代价。
4. 排序和最终预测不读取 `EntryIndex/ExitIndex`。真实索引只在预测结束后用于诊断其排名。
5. 中段只调用 P10 的无损压缩精确闭包。

因此下面的 Accuracy 不是 Oracle 路径回放，而是自动选择 Portal 的真实结果。

## 3. 周期核心下界

只按局部代价排序会优先选择“离端点便宜、但中间周期转移昂贵”的事件。P11 对每个方向、周期数和事件预计算：

```text
entry_lower[e] = min_x PortalCost[e, x]
exit_lower[x]  = min_e PortalCost[e, x]
```

排序分数变为：

```text
source_score = source_local + entry_lower
target_score = target_local + exit_lower
```

这些是严格下界，不会改变合法路径代价。双方向、1～5 周期、行列两组 `uint16` 数据合计仅 `76,800 B`，可以静态嵌入。

## 4. 局部模板召回消融

Beam5 时，真实入口局部连接可达 `185/190`，真实出口可达 `187/190`。把局部候选增至 16 后，两端都达到 `190/190`：

| 局部模板数 | 源端真实连接精确 | 目标端真实连接精确 | 源/目标不可达 |
|---:|---:|---:|---:|
| 5 | 145/185 | 126/187 | 5 / 3 |
| 16 | 157/190 | 141/190 | 0 / 0 |

## 5. 联合入口/出口搜索

独立 Top-K 要求正确入口和正确出口同时落在 Top-K，浪费较大。P11 另外测试：保留 K 个入口，再对这些入口逐行联查全部可达出口。

| 保留入口数 | Accuracy | 完全相同 | MAE |
|---:|---:|---:|---:|
| 1 | 92.874408% | 34/190 | 55.684 |
| 2 | 94.818864% | 41/190 | 41.484 |
| 4 | 96.354760% | 62/190 | 28.026 |
| 8 | 96.991848% | 69/190 | 23.463 |
| 16 | 97.631847% | 85/190 | 18.547 |
| 32 | **98.258958%** | 93/190 | 13.589 |
| 64 | **98.658770%** | 105/190 | 10.274 |

反向“保留出口、扫描入口”较差：K=64 时为 `97.717455%`。说明源端入口比目标端出口更容易压缩，下一轮应围绕“入口 -> 少量条件出口”建立索引。

## 6. 性能和提交判断

当前 P11 研究程序仍逐一调用局部定价器：

- 两端共 3,840 个事件；
- Beam16 平均约 5,466 万次状态转移；
- 优化编译下，190 条样本的单请求研究耗时约数百毫秒，远不满足在线要求；
- Portal 单次查表仍约 16 ns，慢的是局部事件枚举，不是周期矩阵。

因此当前判断是：

- Routing Input 终止接口：**Go**；
- 76.8 KB 周期核心下界：**Go**；
- P10/P11 Accuracy 潜力：**已在目标子集跨过 99%**；
- 当前逐事件局部连接器：**No-Go**；
- 合并进正式提交：**No-Go，继续使用 P8**。

## 7. 下一轮优化顺序

1. 把 1,920 次独立局部定价改成一次批量 DP，同时输出所有 Portal 输入状态的局部代价。
2. 将 1,920 个事件先按 `12 个 x × 方向状态/跨度类` 分层，先选入口组，再展开相位。
3. 为每个 `方向 × 周期 × 入口组 × 目标端口族` 保存少量条件出口；目标是 Top-32 入口每个只检查 2～4 个出口，而不是扫描全部出口。
4. 在独立 Teacher 留出上选择入口数和每入口出口数，再回放 190 条目标集合及完整公开 1M。
5. 只有端到端 1M Accuracy、1 亿时间外推、静态体积和总分都优于 P8，才生成正式提交二进制。
