# SRB Fast V4 评分与提交契约

状态：阶段 A 审计结果，2026-08-27。本文只记录项目内官方材料能够支持的结论；缺失规则不作推测。

## 1. 依据与优先级

1. `最新修改版-赛题一：面向超大规模FPGA的布局布线延时估算算法（紫光同创）(1)(1)(2).pdf`，V0.2，2026-08-26。评分与提交规则以此为最高优先级。
2. `紫光同创-EDA竞赛文件说明/紫光同创-EDA竞赛/【紫光同创】Pango 延时估算check、request与result说明.docx`。
3. `紫光同创-EDA竞赛文件说明/紫光同创-EDA竞赛/【紫光同创】Pango FPGA SRB互联阵列说明文件.docx`。
4. `EDA-PANGO-SRB-Arch-Delay/EDA-PANGO-SRB-Arch-Delay/README.md`。

项目中的 V3 README、验证脚本和已有实现是复现依据，不替代官方规则。

## 2. 正式输入与输出

- 正式输入文件名：`delay_estimate_request.csv`。
- 正式规模：1 亿条延时估算请求。
- 输入列：`From,To`；每行包含一个 from pin 和一个 to pin。
- 端点格式：`SRB_x_y/PORT`。坐标、端口和路由规则由五个架构 JSON 文件定义，不能只凭字符串形状推断合法性。
- 调用形式：`estimate -in ./delay_estimate_request.csv -out ./delay_estimate_result.csv`。
- 结果文件示例列：`From,To,delay`，delay 以 ps 为单位，官方示例为整数。
- 输出必须与输入逐行同序。官方材料没有单独写出“允许重排后恢复”的规则，因此 V4 按严格同序实现。
- 官方材料未明确小数输出精度、舍入方式、不可达端点表示、坏行、重复表头或部分输出的判罚方式。V4 的本地安全契约是：只接受完整合法端点；正常请求每行恰好输出一个非负整数 delay；不静默丢行；解析失败返回非零退出码。该本地契约不是对官方判罚的补充解释。

## 3. 硬性资源限制

- 峰值运行内存不得大于 2 GB；超过即本次运行无效并终止。
- 完整 1 亿条请求的单次 real time 不得超过 30 分钟，即 `limit_time = 1800 s`；超时即本次运行无效并终止。
- 服务器运行波动通过 5 次运行取平均时间处理。
- 官方建议：公开 100 万条约为正式规模的 1%，本地总时间应尽量控制在 18 秒内。
- 若 5 次运行中有至少 2 次发生上述无效情况，作品无效，最终总分为 0。
- 官方材料没有明确仅 1 次运行无效时的时间、准确性和总分聚合方式。

## 4. 官方评分公式

总分采用百分制：

```text
score = 0.80 * acc_score + 0.15 * time_score + 0.05 * consistency_score
```

对第 `i` 条、Golden 延时 `g_i > 0`、预测 `p_i`：

```text
point_i = 1 - tanh(4 * abs(p_i - g_i) / g_i)
acc_score = 100 / N * sum(point_i)
```

官方公式没有定义 `g_i = 0` 时的除零语义。现有 V3 验证器将其参数化为“预测也为 0 得 1，否则得 0”；V4 评测接口保留该策略参数，不能称为官方定义。

有效运行的时间分：

```text
avg_time = 5 次 real time 的平均值
time_score = 100 * (1 - avg_time / 1800)
```

官方材料没有说明是否对 `time_score` 额外裁剪；超过 1800 秒已按无效运行处理。

一致性分：

- 5 次输出完全一致：`consistency_score = 100`。
- 任意结果不一致：`consistency_score = 0`，且 `acc_score` 取 5 次结果的平均值。

因此 V4 的主优化目标是参数化的预计总分，而不是单独的 RMSE 或吞吐量。

## 5. 编译、依赖、训练和离线资产：官方未明确事项

最新版说明中没有明确给出以下规则：

- 指定操作系统、CPU 指令集、编译器版本、C++ 标准或允许的语言；
- 是否允许动态库、Python 运行时或第三方依赖；
- 提交包是否允许附带独立的 Atlas、模型权重、参数表或其他离线生成文件；
- 是否允许把公开 100 万条 Golden 用作训练数据，还是只允许调试和公开评测；
- 可执行文件和附带资产的体积限制；
- 架构 JSON 在正式运行时是否与可执行文件一同提供。

当前 V3 使用 C++17、离线生成的约 624 MiB Atlas、编译进二进制的模型参数，并使用公开 Golden 训练；这只能证明当前项目这样实现，不能证明官方已允许。V4 保留相同能力但在提交前必须向主办方确认，且必须记录训练数据、种子、特征版本和架构指纹。

## 6. V4 本地评分接口要求

统一评测工具必须把以下值作为参数，而不是散落在训练脚本中：

- 准确性权重、时间权重、一致性权重；
- `tanh` 系数 4；
- `limit_time = 1800 s`；
- 正式运行次数 5；
- Golden 为 0 的策略；
- 时间分是否裁剪；
- 无效运行阈值及其最终处罚。

报告必须同时给出 `acc_score`、预计 `time_score`、一致性假设、预计总分、MAE、RMSE、相对误差和误差分位数。若缺少 5 次正式规模运行，只能标注为“预计总分”，不能称为官方成绩。

## 7. 待官方确认问题

1. 公开 Golden 是否允许用于训练、残差拟合和输出校准？
2. 是否允许提交独立 Atlas/模型文件，如何定位和校验这些文件？
3. 官方 Linux/Windows 环境、编译器、CPU 指令集和允许依赖是什么？
4. delay 是否必须为整数，若模型输出小数采用何种官方舍入语义？
5. Golden 为 0、不可达请求、坏行、少行、多行、列名变化分别如何计分或判无效？
6. 5 次中恰好 1 次无效时如何计算 `avg_time`、`acc_score` 和总分？
7. 输出一致性比较是逐字节、逐行字段还是数值一致？
8. 提交包和离线资产是否有独立体积限制？
