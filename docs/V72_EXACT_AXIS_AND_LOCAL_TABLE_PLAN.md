# V72：单轴周期审计与精确局部路由表计划

## 结论

两种单轴周期近似均不足以作为 99.9% 目标的正式算法：

| 路由层方案 | 审计状态数 | 采样竞赛 Accuracy | MAE | 最大误差 |
|---|---:|---:|---:|---:|
| 两轴仿射周期 | 364,953,600 | 96.549788% | 26.324 ps | 779 ps |
| 精确 x，只外推 y | 364,953,600 | 99.077294% | 11.351 ps | 420 ps |
| 精确 y，只外推 x | 364,953,600 | 97.856986% | 12.598 ps | 480 ps |

这说明剩余误差不是再加一条斜率可以解决的连续误差，而是最优路径骨架和方向状态发生离散切换。V71 仿射表以及两个单轴变体都不进入提交版本。

下一步保留两类严格精确的结构：

1. 半径 24 内使用精确的 `160 × 160` 路由状态表，再与源端局部连接和目标端局部连接做固定次数 min-plus 组合；
2. 长距离和 Block 周期段复用 P9/P10 已验证的精确 Portal 闭包，不做线性斜率外推。

## 为什么先替换 Base Atlas

V69 的 Base Atlas 按约 `368 × 448` 个端口组合存储半径 24 的结果，端口组合中存在大量重复的路由状态。精确图只有 160 个 Routing Input 状态，因此先保存路由态核心，再在线组合少量端口连接器，有机会把约 446 MB 的 Base Atlas 替换成小于 100 MB 的只读表，并保持该范围的数值完全一致。

新审计 `audit_exact_local_route_packing.cpp` 会同时测量：

- 原始 `uint16` 表；
- `每个 source/displacement 行一个 uint16 基值 + 7～11 bit 残差`；
- 不可达状态使用全 1 哨兵，不错误地计入稀疏异常；
- 12/13 bit 绝对值布局；
- 原始表的 gzip/zstd 实际压缩体积；
- 生成耗时和峰值内存。

只有无损布局加程序本体严格低于 100 MB，并且端到端回放与 V69 Base 分支逐条一致，才进入 V72。该分支每条查询只允许固定数量数组读取和很小的 min-plus 组合，不加入 A*、Dijkstra 或 Beam。

## 后续 Go/No-Go 门槛

1. **体积**：Linux ELF 小于 100 MB，并保留至少 3 MB 安全余量；
2. **正确性**：半径 24 内所有可覆盖端口组合与 V69 Atlas 位级一致；
3. **速度**：报告解析、连接器组合、查表、格式化、写出和冷启动，外推 10 亿条总时间不高于 V69；
4. **泛化**：公开集、独立源、独立区域三套评估均不降分；
5. **长距离**：只接受 P10 式精确 min-plus 周期闭包，不再接受单斜率近似。

本轮精确全距离审计对应 GitHub Actions run `40445586498`。

三类源端口分别验证了 2,689,120 条直接 Input、2,689,120 条 Output 和 806,736 条间接 Input，均为零差异。表 SHA-256 为 `70093f7b5ab259f70412535ddb76f956bfd91a0c8b4dca05ac2d54c20c4ff752`，对应 GitHub Actions run `40461411363`。

旧 Base Atlas 使用 8 格 Dijkstra 边界时，首次对照有 26,993/6,184,976 条返回 `INF`，而宽边界图能找到有限路径；没有发现新表高估或有限值数值不一致。最终表和验证 Golden 均使用 32 格离线边界，消除了该截断误差。
